# Правила работы с репозиторием

## Источник требований

- `SPEC.md` — источник истины для первой версии сервиса.
- `DESIGN.md` — источник истины по UX/UI; он не меняет бизнес-правила и права доступа из `SPEC.md`.
- Нельзя молча расширять первую версию. Новое продуктовое решение сначала фиксируется в `SPEC.md` и согласовывается с владельцем проекта.
- Отложенные функции и идеи, не входящие в текущую задачу, записываются в `TODO.md`.

## Перед реализацией

- Определите затрагиваемые требования и разделы `SPEC.md`.
- Проверьте допустимые состояния, переходы и серверные ограничения, если задача относится к бизнес-логике.
- Если изменяются бизнес-правила, одновременно обновите `SPEC.md`.

## Стиль Python-кода

- Python-код находится в `backend/`; новый и изменяемый код должен быть совместим с настройками Black, flake8 и mypy из корня репозитория.
- Используйте двойные кавычки для строк, если это не ухудшает читаемость или не требует лишнего экранирования.
- Соблюдайте длину строки в 88 символов, применяйте понятные имена и явные типы для новых функций и методов.
- Не отключайте правила линтеров точечно без обоснованной технической причины.

## Изменения и проверка

- Не изменяйте несвязанный пользовательский код.
- После изменений запускайте подходящие тесты, линтеры, проверки типов, сборку или иные релевантные проверки.
- После изменений Python-кода запустите `./scripts/format-backend.ps1`, затем `venv\Scripts\python.exe -m flake8 backend` и `venv\Scripts\python.exe -m mypy backend`.
- Не реализуйте функции из `TODO.md` без отдельной задачи.

## Frontend: обязательный pipeline

- Frontend находится в `frontend/`; для любой задачи, затрагивающей его код,
  сначала применяйте навык `.agents/skills/frontend-quality` и следуйте
  `frontend/AGENTS.md`.
- Задача с изменениями frontend-кода не завершена, пока `npm run check` из
  `frontend/` не завершится успешно. Команда включает lint, unit/component
  tests и production build.
- Для изменения пользовательского поведения добавляйте или обновляйте
  поведенческий тест Vitest + Testing Library. Для изменений интерфейса также
  выполняйте UI/UX и accessibility-ревью, а для критичного пользовательского
  сценария — браузерную проверку, когда тестовое окружение доступно.

## Завершение задачи

В итоговом сообщении обязательно перечислите:

1. внесённые изменения;
2. выполненные проверки и их результаты;
3. известные ограничения или нерешённые вопросы;
4. следующий практический шаг.

Когда пользователь просит сохранить итоги сессии разработки, используйте навык `.agents/skills/session-summary` и сохраняйте итог в `docs/sessions`.
